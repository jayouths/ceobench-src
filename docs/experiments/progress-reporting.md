# 正式实验进度汇报规范

## 1. 目的

本规范用于汇报并行运行的 Baseline 与创新实验组。每次汇报必须同时回答三类问题：实验推进到哪里、模型调用是否阻塞、企业经营是否接近破产。

汇报只读取已经持久化的数据库、检查点和日志。不得为了生成汇报而修改运行状态、重启进程或中断在途调用。

## 2. 比较口径

1. 先分别读取两组实验最新完成并持久化的模拟日。
2. 取两者较小值作为“最新可比节点”。经营结果只在该节点比较，不能拿 Baseline Day 112 与 Analysis Day 98 直接比较。
3. 再分别报告两组各自的最新进度，以说明领先的一组已经运行到哪里。
4. “累计”必须写清起点和终点，例如“本次正式实验从 Day 0 至 Day 98 累计”，不能只写“累计成本”。
5. 周内尚未提交的数据标记为“在途”，不与已完成节点混算。

## 3. 固定汇报结构

汇报先用一小段说明“相比上次汇报发生了什么变化”，再严格按“最新可比节点 → Baseline 最新情况 → Analysis 最新情况”的顺序组织。变化摘要至少包含两组各自新增完成的模拟天数、最新现金方向、运行状态变化和新出现的风险；没有变化也要明确说明。每一部分都要包含该节点对应的经营结果、经营成本结构和 API 成本；不能用某组更晚节点的数据替代同节点比较，也不能只在文末给一份脱离节点的成本汇总。

### 3.1 最新可比节点

在同一模拟日对比：

- 现金、累计收入、累计支出和净现金流。
- 分别列出两组的经营收入结构和经营成本结构。收入至少区分订阅收入与广告收入；成本至少区分研发、运营、广告、容量、算力、获客、市场研究和研究项目。一次性研究投入必须与持续经营成本分开解释。
- 成本结构同时报告“从 Day 0 至可比节点累计”和“最近 7 天”两个窗口；只看累计值会掩盖 Agent 最近是否已经削减或增加支出。
- 有效订阅或订阅席位、近期新增客户和流失情况。
- 未解决工单、服务质量和其他能够解释经营差异的核心指标。
- Baseline 与 Analysis 的差值及简短解释；证据不足时只描述现象，不推断因果。

### 3.2 Baseline 最新情况

- 最新已完成模拟日、当前正在处理的周或调用。
- 进程是否存活，日志是否持续更新。
- 当前调用目的、已经等待多久、是否接近配置的超时上限。
- 最近一段时间的调用次数、重试次数和耗时分布；不能只凭一次慢调用判断卡死。
- 最新现金、收入、支出、订阅、工单，以及明显的经营风险。
- 单独分析 Baseline 的主要收入来源、累计成本构成、最近 7 天成本构成及其变化，说明当前现金流压力主要来自哪些支出；没有证据时不推断支出的决策动机。

### 3.3 Analysis 最新情况

报告内容与 Baseline 相同，并额外说明：

- 当前处于信号提取、四角色报告、经营画像重构，还是 Bash Agent 决策。
- 四角色串行或并行配置及实际调用状态。
- JSON 修复调用、超时重试和失败降级是否发生。
- Analysis 各阶段额外消耗的 Token、时间和费用。
- 单独分析 Analysis 的主要收入来源、累计成本构成、最近 7 天成本构成及其变化，再与其收入规模、客户规模和服务压力结合判断成本是否可持续。

### 3.4 简单判断

每次结尾给出两个独立判断：

- **运行判断**：正常推进、调用较慢、疑似阻塞或已经失败，并说明证据。
- **经营判断**：破产风险低、中或高，并说明现金缓冲、近期净现金流、固定成本、可调支出、客户流失和工单压力。

风险等级不是只看现金余额：现金仍为正但持续大额净流出、收入下降或服务压力失控时，也应提高风险判断。

## 4. 成本口径

“成本”包含两套不能混用的口径：

1. **模拟企业经营成本**：来自 `world.nmdb` 的 `ledger`，用于解释企业现金变化。必须按支出类别拆分，并分别报告累计与最近 7 天结构。
2. **真实模型 API 成本**：来自模型调用日志和平台账单，用于衡量实验成本及创新模块的额外开销。不得并入模拟企业现金或经营利润。

费用必须分开报告：

| 口径 | 数据来源 | 用途 |
|---|---|---|
| 日志理论成本 | 运行日志中的 Token 用量 × 仓库配置的官方模型单价 | 保持论文实验之间的统一比较 |
| 平台估算成本 | Token 用量 × AutoDL 对应输入、缓存输入和输出单价 | 与平台账单对账 |
| 平台实际费用 | AutoDL 账单或消费统计 | 确认真实人民币支出 |
| 冻结金额 | 平台仍为在途请求预留的金额 | 仅说明资金占用，不算已结算费用 |

输入 Token、缓存输入 Token、输出 Token必须分别计价。Provider 未返回的用量字段记为未知，不得静默按 `0` 推导“没有消耗”。

## 5. 调用阻塞判断

一次调用耗时长不等于进程卡死。按以下顺序判断：

1. 进程是否仍存活。
2. 当前请求是否仍在配置的超时窗口内。
3. 服务端或轨迹日志是否出现成功回执、重试、限流或错误。
4. 同类调用最近的典型耗时是多少，当前耗时是否明显异常。
5. 检查点或数据库是否在一次完整周推进后继续更新。

只有进程退出、请求超过超时且未被正常处理、日志长期无更新，或错误反复重试而无法推进时，才报告为明确卡点。

## 6. 数据来源优先级

1. `world.nmdb`：现金、账本、订阅、客户、工单和服务状态的权威来源。
2. `checkpoint.json`：已完成边界和恢复状态。
3. `logs/trajectory_*.jsonl`：调用、工具、重试和事件的真实发生顺序。
4. `logs/performance_*.jsonl`：周级、模块级用量和耗时汇总。
5. `result.json`：仅在实验结束后作为最终汇总。
6. AutoDL 账单页面：平台实际扣费和冻结金额。

## 7. 精简模板

```text
相比上次：两组分别从 Day X/Y 推进到 Day A/B；现金、运行状态和主要风险发生了什么变化

最新可比节点：Day N
- Baseline：现金 / 收入 / 支出 / 订阅 / 工单
- Analysis：现金 / 收入 / 支出 / 订阅 / 工单
- 差异：只陈述有数据支持的主要变化
- 经营成本结构：分别报告两组累计结构与最近 7 天结构，并分析主要成本来源

Baseline 最新情况：Day X
- 运行：当前调用、耗时、重试、是否有卡点
- 经营：收入结构、累计与近期成本结构、现金趋势、破产风险

Analysis 最新情况：Day Y
- 运行：当前模块、耗时、重试、是否有卡点
- 经营：收入结构、累计与近期成本结构、现金趋势、破产风险

成本：
- 日志理论成本：范围与币种
- 平台估算成本：范围与币种
- 平台实际已结算：范围与币种
- 冻结金额：单独列示

结论：运行判断 + 经营风险判断
```
